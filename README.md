# TAD6S4N模块（fnOS）

这是一个面向飞牛 fnOS 与 TAD6S4N10G 的第三方模块。它按 RR CPUinfo 的口径显示 Intel Processor N100、N150 与 Intel Core i3-N305 的 CPU 核心最高温度，同时保留 Package 原始温度供核对；还可限制 Package 功耗、按 HDD/NVMe/CPU 三温度曲线控制一个或多个风扇、显示硬盘物理仓位与活动状态，并配置机箱 GPIO 按键映射。

当前版本：0.10.19

界面中的功耗设置、风扇控制和按键映射分别独立保存；保存当前页面不会覆盖另外页面尚未提交的调整。关于页的“检查更新”只在用户点击后请求最新 Release，不会自动联网检查。

配置界面采用 fnOS 原生浅色单层布局，侧栏提供监控面板、风扇控制、按键映射、功耗设置、调试和关于六个页面。桌面侧栏保留版本与健康状态，手机端这两项只在关于页显示；GitHub 仓库和检查更新也放在关于页。侧栏和内容区独立滚动，硬盘仓位图在桌面并排居左、窄屏上下排，风扇曲线随内容区宽度自适应。

## 下载与安装

从 [GitHub Releases](https://github.com/luodaoyi/TAD6S4N10G-fnos/releases) 下载最新的 `tad-module.fpk` 和 `tad-module.fpk.sha256`，校验 SHA256 后，在飞牛应用中心选择手动安装。

仓库的 GitHub Actions 会在针对 `main` 的 Pull Request、推送到 `main` 或推送 `v*` 标签时执行测试和打包；推送与 `manifest` 版本一致的 `v*` 标签时，会自动创建 Release 并附加插件包。

## Debian 原生 TUI

`debian-tui/` 提供普通 Debian 环境下的终端面板适配。它复用主线 `tad-module`，通过 Unix Socket 读取 `/api/status`，不直接执行 `smartctl`；`tank` 只负责读取缓存状态并渲染终端，不直接读写硬件。硬盘温度、SMART 健康和休眠状态由主线后端统一检测与缓存。使用说明见 [`debian-tui/tui-readme.md`](debian-tui/tui-readme.md)。

### Debian 后端必须使用 root

Debian TUI 的 `tad-module` 后端必须以 root 启动，这是官方 `serve()` 的硬性要求，不是可选的 systemd 配置。后端启动时会强制检查 root，并统一管理 `/sys`、`/dev`、RAPL、coretemp、hwmon/PWM、GPIO 和 SMART 等硬件接口；服务生命周期还包含启动时应用状态、后台重应用/风扇/硬盘/GPIO 轮询，以及停止时恢复原始状态。以普通用户启动会在创建 `/api/status` Socket 之前直接退出并报告 `root privileges are required`。

安装脚本默认写入 `enabled=false`、风扇和 GPIO 关闭的监控配置，这只表示默认不会主动应用功耗、风扇或 GPIO 设置，不能取消后端的 root 启动要求。`tank` 本身是面向管理员的只读终端工具；root 用户可直接运行，获授权的普通 SSH 用户也可以通过 `www-data` Socket 组读取状态，但后端服务始终以 root 运行。

## 默认策略

| CPU | PL1（持续） | PL2（短时） | 可调 PL1 | 可调 PL2 |
| --- | ---: | ---: | ---: | ---: |
| N305 | 15 W | 15 W | 6–硬件上限 W | PL1–35 W |
| N150 | 6 W | 15 W | 4–硬件上限 W | PL1–25 W |
| N100 | 6 W | 15 W | 4–硬件上限 W | PL1–25 W |

插件会读取 `constraint_*_max_power_uw`，当内核提供了有效上限时，界面会收敛预设值，后端也会拒绝超过该上限的配置。只支持明确识别出的 N100/N150/N305；其他 CPU 会拒绝安装或启动。

N305 默认将 PL2 与 PL1 同样限制为 15 W，避免 CPU 与核显联合负载在短时窗口内放行过高的 Package 功耗。

## 温度显示口径

在已验证的 fnOS 主机上，系统温度服务会枚举 `coretemp`，但只读取匹配到的首个 `temp*_input`；该节点是 `Package id 0`。飞牛资源监控再把这个 Package 热点作为 CPU 温度显示，并以 65°C/75°C 着色告警。Linux `coretemp` 本身读取 Intel 数字温度传感器，不会把 CPU 与 GPU 温度相加。

RR 的 CPUinfo 实现会筛选标签为 `Core N` 的温度并取最大值。本插件迁移相同口径：主卡片显示所有 `Core N` 中的最高温度，另一个卡片显示所有 `Package id N` 中的最高原始值，诊断区列出每个 `coretemp` 节点方便核对。若系统没有暴露任何 `Core N` 标签，才回退显示 Package 温度并明确标注。

插件不会修改飞牛的私有温度服务、资源监控前端或告警阈值，因此飞牛桌面原有的 Package 温度和红色告警仍会存在；请以插件中分开的两组读数判断二者差异。

## HDD/SATA、NVMe 与 CPU 三温控曲线

风扇功能默认关闭。安装与启动时，本插件会在未检测到独立 [fnos-it87-kmod](https://github.com/IamAyang233/fnos-it87-kmod) FPK（或已加载的 it87 模块）的情况下，用内置源码经 DKMS 编译并 `modprobe it87`；已装独立驱动则跳过，避免双开 DKMS。内核升级后会在 start/upgrade 时比对记录的 kver 并 `dkms install --force` 自愈。停止或卸载本插件**不会** `rmmod it87`。插件仍自动检查 IT87 hwmon 节点；若驱动仍不可用，风扇页会提示检查 `dkms`/`gcc`/`linux-headers-$(uname -r)`，并保留独立驱动包链接作为兜底。驱动已检测但没有完整 PWM/RPM 通道，或通道转速均为 0 RPM 时，也会给出对应的接线/适配提示。驱动可用后，插件只列出同时具有 `fanN_input`、`pwmN` 和 `pwmN_enable`，且当前转速大于 0 RPM 的通道；已勾选风扇瞬时掉到 0 RPM（停转或故障保护）仍会保留在列表中，未接线且持续 0 RPM 的通道不会出现。CPU、HDD 和 NVMe 曲线可分别选择一个或多个风扇；单风扇旧配置会自动迁移为三条曲线都绑定原通道，不会写入未接线的风扇接口。

默认最低转速为 40%（可手填，硬性下限仍是 30% 防停转）。默认 CPU 曲线为 40°C/40%、55°C/70%、70°C/85%、80°C/100%；HDD 与 NVMe 默认曲线均为 25°C/最低转速、35°C/85%、50°C/100%。从 0.10.36 及更早版本升级时，只有**完全没改过**的风扇默认值（最低转速 60% 与三条 60% 起步的默认曲线）会整体换成新默认；只要动过最低转速或任意一条曲线，升级就一个字都不改。三条曲线分别计算目标 PWM，插件始终使用最高值，因此 CPU、前置 SATA 盘或 NVMe 任一方先升温都会提高风扇转速。紧急满速温度为 85°C，风扇采样间隔为 2 秒。CPU 控制温度取所有 `coretemp` 节点中的最高值，不读取无标签的 IT87 温度，也不会把 CPU 与 GPU 温度相加。

三条曲线按 HDD/SATA、NVMe、CPU 单列全宽排列（标签栏与编辑器顺序一致，默认停在第一张），可直接拖动图上的圆点调整；节点带有扩大的鼠标和触控命中区域，并会自动保持温度严格递增、转速不下降，受最低转速和紧急满速温度约束。每条曲线都可增加或删除节点，支持 2–8 个节点；鼠标、触屏和方向键均可操作。HDD 曲线下可分别选择 SATA 1–6，NVMe 曲线下可选择 M.2 1–4，控制只取已勾选槽位的最高温度；全部取消则该类硬盘曲线不参与风扇控制。槽位旁显示最近一次读取的温度，缓存每 60 秒刷新，不会为了 2 秒风扇轮询频繁唤醒 SATA 硬盘。旧配置升级后默认全选全部十个槽位，保持原有温控行为。

标签栏下面是曲线模式与自定义曲线两行工具：

- **曲线模式（静音 / 平衡 / 性能）**：点一下就把三条曲线的全部节点整体换掉（静音＝低转速优先、晚一点拉高；平衡＝常温低速、升温及时提速；性能＝高转速优先）。每档都按当前「最低转速」当地板生成，所以先改最低转速再套预设，地板会跟着走。套用只改界面，仍要点「保存风扇控制」才下发。
- **自定义曲线 1–3**：点「存」把当前三条曲线记进该槽位，点槽位名字把它们载回来，点「导」单独把这个槽位导出成 JSON。槽位保存在浏览器本地（`localStorage`，键 `tad-fan-curve-slots`），坏数据（节点数不在 2–8 之间）整槽作废；换浏览器或清站点数据会丢，需要长期保存请用「导」导出文件。
- **导出曲线参数**：把界面上当前的三条曲线加最低转速、紧急满速温度、采样间隔一起导出成 JSON 文件（`tad-module-fan-curves-<时间戳>.json`），便于备份、比对或反馈问题时附上。

风扇控制业务仍只读写驱动已暴露的标准 hwmon 节点。内置 IT87 安装可能写入本插件可识别的 `/etc/modprobe.d/tad-module-it87.conf` 与 `/etc/modules-load.d/tad-module-it87.conf`（含必要的 `ignore_resource_conflict` / 探测到的 `force_id`）；不会修改 BIOS、GRUB 或飞牛系统服务。第三方驱动源码与 GPL-2.0 全文见 `third_party/it87/`。

每次打开插件界面时，插件都会检查 CPU `coretemp`、IT87 驱动、风扇 PWM/RPM 通道、硬盘仓位枚举及已识别硬盘的 SMART/NVMe 温度。发现异常不会自动弹窗，只会把状态改成“需要检查”；桌面可在侧栏悬停或点按查看项目，手机端请到关于页查看。提示只代表插件当前没有读到相应标准接口；空仓不会被当成温度故障，具体问题仍需结合驱动、接线和槽位映射判断。

## 硬盘面板

插件结合 `/dev/disk/by-path` 与 sysfs PCI 拓扑映射 TAD6S4N10G 的物理仓位：前置 SATA 仓动态识别 ASMedia ASM1166（`1b21:1166`）控制器的 ATA 端口 1–6；四个 M.2 仓按主板固定走线锚定，仓位 N 对应稳定根端口 `0000:00:1d.(N-1)`，不依赖会随网卡插拔变化的下游总线号。空仓根端口即使不被固件枚举，也会按固定走线判定为空；挂在未知根端口上的 NVMe（例如 PCIe 转接卡）不会显示为机箱 M.2 仓。M.2 3/4 切换为 SATA 模式时，也会识别 Intel 原生 SATA 控制器的对应端口；同一槽位检测到 NVMe 时优先按 NVMe 映射。

硬盘面板用前置 SATA 6 → 1 与 M.2 4/2/3/1 的图形盘位卡片动态显示温度、使用/插入/告警状态及各档负载与休眠、未知状态；前置仓与 M.2 卡片同为固定三行槽位（仓号/状态/温度），槽位高度恒定，温度为空（如休眠、空仓）也保留位置，各仓状态词与仓号横向对齐。仓位颜色：绿色为健康使用中，灰色为已插入未使用，蓝色为休眠，深灰为空置（空仓与在位仓使用同几何尺寸的托盘底图，可见高度一致），红色仅表示故障或高温（SATA ≥ 55°C、NVMe ≥ 70°C），繁忙不再标红。健康告警在列表中显示为短标签，点击后弹窗查看完整信息。详情表格继续显示 Linux 设备名、型号、序列号、容量、阵列/挂载用途、活动、繁忙度、SMART 健康与温度。繁忙度与飞牛资源监控、iostat %util 同源，按采样窗口内 `/sys/class/block/*/stat` 的 io_ticks 占比计算。界面每 5 秒获取一次状态，但后台 SMART/温度缓存约 60 秒刷新，不能视为秒级实时；普通刷新不会为了读取健康或电源状态强制唤醒休眠盘，按键动作中的“SMART 检查”会执行一次主动检查；休眠盘温度显示为不可用，不计入“未读取到温度”故障提醒。活动状态按繁忙度（界面四舍五入后的百分比）划分六档：0% 为空闲，1–10% 为轻载，11–50% 为中载，51–70% 为高载，71–99% 为繁忙，100% 为满载。繁忙不再改变仓位颜色。SATA 休眠来自 `smartctl -n standby` 返回的电源模式。仓位映射仅适用于该主板和背板，不能按设备名 `sda/sdb` 猜测物理位置；PCI 拓扑缺失或存在多个同型号控制器时会显示“未知”并给出诊断信息，不会把无法判定的仓位伪装为空仓。

## GPIO 按键映射

按键功能默认开启。插件以 root 访问 `/dev/port`，每 100 ms 读取固定 GPIO 并进行 100 ms 消抖：复制按键为 `0xA04/bit6`，网络按键为 `0xA00/bit3`，后置重置按键为 `0xA03/bit6`（三个位号均已在实机按键核对）。松开时不足 3 秒即为短按并直接执行该键的短按动作；按住达到 3 秒、9 秒、15 秒则分别执行对应长按动作。四个档位均可独立配置，开箱默认**只有网络键的短按**绑好动作（刷新 SD 卡），其余按键与档位一律无动作，避免「按一下不知道会做什么」，需要什么自己绑。每次按键确认或触发时，都会通过 Linux PC Speaker 以 440 Hz 滴滴滴响 3 声（每声 200 ms、间隔 100 ms），并以 `/dev/port` 的 `0xA00/bit0` 闪灯 3 下（亮/灭各 500 ms）—— 表现与 RR 官方插件 `tad6s4n10g` 的 `btnBeep 3` / `btnLed 3` 一致；反馈设备不可用时只记录日志，不阻止动作执行。“保存按钮控制”就在按键表格正下方，保存结果提示紧跟其后。

### 刷新 SD 卡（重新识别 USB 读卡器）

USB 读卡器换了 SD 卡之后，卡有时要等很久、甚至要把读卡器重新插拔才被系统认出来——读卡器换了介质不一定会重新上报 LUN，内核也就不会重新扫描。作者原版 RR 插件 `tad6s4n10g` 的习惯是长按网络键 3 秒处理这件事，这里沿用同一思路：把读卡器 USB 设备的 `authorized` 置 0 再置 1（等效拔掉再插上），让内核重新枚举，并对 USB 存储控制器补一次扫描。默认绑定在**网络键短按**上（换卡后随手按一下，不必按住 3 秒），按键控制页也提供「刷新 SD 卡」按钮，不必走到机器跟前。

**从 v0.10.25 升级**：那一版把该动作填在了网络键长按 3 秒上。升级后如果那一档仍然是「刷新 SD 卡」，会被自动挪到短按并腾空长按档位（短按档位当时还挂着我们的旧默认值「重新应用插件配置」时才会被顶替）；你要是自己把它改成过别的动作，则一律不动。这条搬迁只做一次（旧标记处理完即摘除），之后你自己再把某个键的长按 3 秒设成刷新 SD 卡也不会被改写。

安全性上做了四层限制：只处理 USB 接口类 `08`（大容量存储），SATA/NVMe 上的系统盘与数据盘绝不触碰；正在使用中的设备一律跳过并在日志里说明，判定不只看 `/proc/mounts` 上的直接挂载，还会看块设备及其分区在 `/sys/block/<盘>/holders/` 下是否被 md（RAID 成员）、dm（LVM PV、dm-crypt）占用、以及是否出现在 `/proc/swaps` 里（这几类在挂载表里显示成 `/dev/md*`、`/dev/mapper/*` 或压根不出现），不会把仍在服役的移动硬盘踢下线；重扫只落在与读卡器相关或 `proc_name` 带 usb 的控制器上，不会去动本机那 32 个 ahci 控制器。原版插件把 PCI 路径写死成 DSM 虚拟机的 `0000:00:0d.0/usb2/2-1/2-1.4`，这里改成从 USB 设备树动态发现。

判断「卡有没有认出来」看的是块设备容量而不是设备名：空读卡器的 `/dev/sdc` 节点其实已经存在，但 `size` 为 0、也不出现在 `/proc/partitions` 里；插好卡并被正确读出后容量才变成真实值。刷新后会轮询最多 6 秒，一旦读到容量就立刻返回，所以换一张容量不同的卡（设备名不变）也能被认出来。刷新的结果会写进运行日志（重新识别了哪个读卡器、跳过了谁、有没有读出介质），结束时闪 3 下 + 滴滴滴 3 声，失败则一声长鸣——写 `/sys` 失败时不会伪装成成功。

### 存储设备插入提示音

识别到新插入的存储设备时用同一只机箱蜂鸣器提示，两种节奏闭着眼也能分辨：

| 事件 | 提示音 | 判定 |
| --- | --- | --- |
| 移动存储：U 盘、读卡器、移动硬盘 | 长响一次（880 Hz / 800 ms） | 内核 `removable` 标志为 1，或块设备挂在 USB 总线下面（很多 USB 硬盘盒把 `removable` 报成 0） |
| 内置存储：机箱里的 SATA 与 M.2 仓位 | 连续响两声（880 Hz / 每声 220 ms） | 其余真实块设备 |

判定靠 `/sys/block` 前后两拍（每 2 秒一拍）的快照差分，所以：

- 开机时已经在的盘不会响——首拍只建立基线；
- 拔出设备不提示，只在「新出现」时响；
- 没插卡的读卡器容量为 0，不算插入；插上卡（或换一张容量不同的卡）才提示；
- 托架换盘、设备名没变但容量变了，同样算一次插入；
- `loop`、`ram`、`zram`、`dm-`、`md`、`sr`、`nbd`、`rbd`、`fd` 这些内核虚拟设备不参与监视；
- 采样失败时保留旧基线，恢复后不会把已在的盘当成新插入而乱响。

开关在按键映射页（默认开启），它与「启用按键映射」相互独立：不看屏幕也想知道插的盘认没认上时可以一直开着，嫌吵随时关掉。最近几次插入事件会显示在开关旁边。

注意「刷新 SD 卡」也会触发它：重新识别时块设备会先消失再带着容量回来，落地成一次「新插入」，所以除了刷新本身的三声滴滴滴，还会再响一次长鸣——正好说明卡确实被读出来了。

除无动作、仅记录日志、刷新硬盘仓位、刷新仓位并检查 SMART、重新应用插件配置、刷新 SD 卡等内置动作外，按钮控制页还提供自定义 Bash 脚本管理。用户可新增、编辑和删除脚本，再按脚本名称将其绑定到任意按键及按压时长；编辑器使用等宽字体并提供基础 Bash 语法高亮。脚本及映射只有在点击“保存按钮控制”后才会持久化。

自定义脚本由插件服务以 root 通过 `/bin/bash --noprofile --norc` 执行，单次最长 30 秒，标准输出和错误输出合计最多保留 64 KiB。执行时提供 `TAD_GPIO_BUTTON_ID`、`TAD_GPIO_STAGE`、`TAD_GPIO_DURATION_MS` 和 `TAD_GPIO_SCRIPT_NAME` 环境变量。脚本可以修改或删除系统数据，插件不会分析脚本是否安全，请只保存完全信任的内容。

### 备份任务

按钮控制页的「备份任务」提供图形化配置，不需要写脚本：点「浏览…」在位置对话框里选源和目标，再挑一种复制方式。任务保存后，把某个按键的短按或长按动作选成「备份：任务名」即可；按一下按键就开始备份，结束时闪 3 下 + 滴滴滴 3 声。也可以点卡片上的「立即运行」手动执行，或点「试跑」只列出将复制的文件而不写入任何内容（试跑不响蜂鸣、不闪灯，也不会顶掉「上次备份」的结果）。

**位置浏览**：对话框默认只列出与飞牛文件管理器一致的四大类位置，不把系统目录摆出来让用户选：

| 位置 | 识别方式 |
|---|---|
| 我的文件 | 内部存储卷根 `/volN` 下的 uid 目录（如 `/vol1/1000`），副标题显示用户名 |
| 团队文件 | 内部存储卷根下其余面向用户的目录（自动过滤 `@`、`.`、`#` 开头以及 `docker`、`thumb` 等系统目录） |
| 外接存储 | `/proc/mounts` 中可移动介质（读取 `/sys/block/<disk>/removable`），按卷标/UUID 识别，换接口或换挂载路径不影响 |
| 远程挂载 | rclone 云盘与 SMB/NFS/WebDAV 等网络挂载（如 `/vol02/<id>`） |

在「外接存储」里选中的路径会按卷标/UUID 记录介质本身加卷内子目录，而不是记死挂载路径。确有需要时可点「高级：原生目录模式」进入整个文件系统，进入前有风险提示与二次确认，进入后界面上会常驻警告条。

**新建文件夹**：浏览到目标位置后，如果还没有合适的目录，不必切到文件管理器去建、建完再回来找——对话框底部的「新建文件夹」直接建，输入名字回车即建，建完自动进入该目录，接着点「使用当前目录作为目标」即可。约束与浏览一致：

- 默认只在四大类位置内可建；进了「高级」才放开到整个文件系统
- 文件系统根目录 `/`，以及 `proc`、`sys`、`dev` 等伪文件系统永远不建
- 只读卷直接拒绝（提示「该卷为只读」）
- 名字不能含路径分隔符，不能用 `@`、`#` 开头，也不能用 `docker`、`thumb` 这类会被浏览列表隐藏的名字（否则建完在列表里看不见）
- 同名文件或文件夹已存在时报错，绝不覆盖；只创建一层、不做递归，手滑写错路径时不会闷声建出一条目录链

| 复制方式 | 行为 | 底层命令 |
|---|---|---|
| 按日期归档（硬链接增量） | 每次在目标下生成 `YYYY-MM-DD_HHMMSS` 快照；未变化的文件通过 `--link-dest` 与上一份快照做硬链接复用，只真正复制新增或改动的文件，因此多份快照几乎不额外占用空间。源文件不动 | `rsync -a --link-dest=<上一份快照>` |
| 按日期转移归档（复制后清空源） | 先在目标下建一个 `YYYY-MM-DD_HHMMSS` 日期目录，把源文件复制进去之后删除源里的文件 | `rsync -a --remove-source-files --ignore-times` |
| 同步文件 | 让目标与源完全一致，目标里多出来的文件会被删除。源文件不动 | `rsync -a --delete` |
| 直接复制覆盖 | 把源内容复制进目标，目标中多出来的文件原样保留；可勾选是否覆盖同名文件 | `rsync -a`（不勾选时追加 `--ignore-existing`） |
| 移动覆盖（复制后删源） | 复制成功后删除源里的文件，同名文件覆盖、目录结构保留 | `rsync -a --remove-source-files --ignore-times` |

**归档保留份数（0 = 不限）**：跟着你选的归档档位走——选中「按日期增量归档」它就出现在那一行正下方，选中「按日期转移归档」就出现在那一个的正下方，换到其它复制方式整行自动收起。只对这两种归档模式生效：填 N 表示只保留最近 N 份快照，更早的自动清理（0 = 不限）。文字与输入框压在同一行，不额外占一整行。普通备份任务与自动备份两张卡片行为完全一致。

**源介质标识**：「在源中创建标识文件」开关和它的标识输入框排在同一组里，开关在上、标识内容在下。想避免「认错盘」时打开开关即可——不需要自己写内容，系统会生成一串随机标识（如 `tad-3f1a9c2b0d4e`）并写进源里的 `.tad-backup/source`（该文件不会被复制进备份）。之后每次备份前会先核对这个文件，对不上就拒绝执行；开关关掉＝留空＝不校验。写入刻意只由用户明确打开开关触发：如果在执行备份时自动补写，那么插错盘也会被写成「对的盘」，校验就完全失去意义。早期版本写在源根的 `.tad-backup-source` 继续能读，下次写入时自动收进新目录。

**元数据统一放 `.tad-backup/`**：源介质标识是 `.tad-backup/source`，自动备份的打标信息是 `.tad-backup/mark.json`——卷根只多这一个隐藏目录，不在用户自己的目录列表里到处丢点文件。这个目录同时进了备份排除列表和目录浏览黑名单（浏览窗口看不到，也选不成备份目标）。

**安全限制**：目标不能是系统目录、卷根或整个「我的文件」根目录（例如 `/`、`/usr`、`/vol1`、`/vol1/1000`），源与目标也不能互相包含，避免同步模式误删源数据或无限递归复制。**移动类模式（移动覆盖 / 按日期转移归档）会删除源里的文件**，所以源不能是整个存储卷（`/vol1`）、整个「我的文件」「团队文件」根目录或远程挂载根目录，也不能是系统目录——这些位置一次误选就会搬空，必须进到具体子目录；可移动卷的根目录不受此限制。移动模式固定覆盖同名文件（覆盖开关自动失效），且只删除已被 `rsync` 确认复制成功的文件，中途出错时没传完的文件仍留在源里。备份通过系统自带的 `rsync` 以 root 执行，单次最长 6 小时；一次只允许一个任务在跑。

### 自动备份（打标卷）

普通备份任务把目标写死成某一块盘，插上另一块盘就不认。「自动备份」解决的是**一个按键服务任意多块盘**：给每块 U 盘/移动硬盘**打标**，再建一条规则绑定到按键。按键一按，系统自动扫描当前插着的**所有打标卷**，逐个执行；一块盘失败不影响其它盘，最后把所有失败一起报出来。

**打标信息落在卷内的统一元数据目录**：`.tad-backup/mark.json`（别名、打标时间、已打标的子目录）。卷根只多这一个目录，不会再往用户自己的目录列表里丢点文件，也和源介质标识共用同一个位置。旧位置都继续认：`.tad-auto-backup/mark.json` 与更早留在卷根的 `.tad-auto-backup` 普通文件按原样读出来，下次打标时自动收敛到新目录。取消打标只删自己的 `mark.json`，目录里还留着源介质标识就原样保住。

**打标**：在自动备份卡片点「给整块卷打标…」，在位置对话框里随便选中卷里的哪个目录都行——只用来认定这块盘。打标时可以填**别名**（最多 32 字），列表与日志里都用别名显示。设备列表会列出**所有存储设备**：在线的（含尚未打标、以及不支持打标的内置盘，都会标明状态）、已打标但当前离线的（记录存在 NAS 侧，重启后仍在）。在线设备可「取消打标」；离线设备可「取消打标（设备不在，下次上线自动清除）」——登记后等它下次插上自动删除标记，登记本身还能撤销。打标失败会明确说明原因：不在可移动存储上、该卷以只读方式挂载、没有写入权限、空间不足。

**子目录打标**：点「给子目录打标…」给某个子目录打标（例如 DCIM），这块盘就**只操作这些子目录里的内容**；可以逐个累积多个（例如 DCIM、VIDEO），也能在列表里点子目录上的「×」单独取消。卷根打标＝整块盘参与。导入 NAS 时**保留目录名**（落成 `目标/DCIM/…`），一块盘的所有子目录在同一次 rsync 里传完——归档模式进同一份快照，移动模式也只删这些子目录里已成功复制的文件。不在打标范围内的文件（卷根的其他文件）完全不动。

**方向**（建规则时二选一）：

| 方向 | 含义 | 卷内子目录 |
|---|---|---|
| 打标卷 → NAS | 把打标盘里的资料导入 NAS（相机卡导入等场景） | 由**打标时标记的子目录**决定（整卷打标＝整块卷），编辑器里不用填 |
| NAS → 打标卷 | 把 NAS 上选定的目录备份进打标盘 | 目标子目录，留空 = 卷根，**不存在时自动创建** |

升级前在老规则里手填过「卷内子目录」的仍然生效并保持原语义（不加尾斜杠＝把该目录的内容铺进目标），不会被新的打标子目录覆盖。

**复制方式**五种，顺序与行为跟普通备份任务完全一致。两种「移动」模式两个方向都能用，但「NAS → 打标卷」的源在 NAS 上，删源不可逆，需要**逐条勾选确认**（见下）：

| 复制方式 | 行为 | 底层命令 |
|---|---|---|
| 按日期增量归档（硬链接增量） | 目标下生成 `YYYY-MM-DD_HHMMSS` 快照，未变化文件硬链接复用 | `rsync -a --link-dest=...` |
| 按日期转移归档（复制后清空源） | 在目标下建一个日期目录，把源文件复制进去之后删除源里的文件 | `rsync -a --remove-source-files --ignore-times` |
| 同步文件 | 目标与源完全一致，目标里多出来的文件会被删除 | `rsync -a --delete` |
| 直接复制覆盖 | 把源里的内容复制进目标，同名文件覆盖，目标多余文件保留 | `rsync -a` |
| 移动覆盖（复制后删源） | 复制成功后删除源里的文件，同名文件覆盖，目标多余文件保留 | `rsync -a --remove-source-files --ignore-times` |

**移动模式的安全边界**：只删除已被 rsync 确认复制成功的文件（`--remove-source-files`，复制成功一个删一个），中途出错时没传完的文件仍留在卷里；空目录结构保留，盘还能继续用。移动模式固定覆盖同名文件且强制重新传输（`--ignore-times`）：rsync 默认按「大小 + mtime」判定同名文件已同步，会跳过传输却仍删源，导致目标残留旧内容——已修复杜绝。普通备份任务同样支持这两种模式，源位置受上一节「安全限制」约束。

**「NAS → 打标卷 + 移动模式」为什么单独要确认**：这个组合的源是 NAS 上的原始资料，删掉不可逆，而自动备份是「一条规则 × 一次按键 × 当前插着的每块打标盘」——第一块盘搬空源之后，后面的盘只会「成功」地传 0 个文件，界面上却全部显示成功。因此：① 保存规则时必须勾选「我确认：这条规则可以删除 NAS 上的源文件」（按键触发时没有界面能弹窗，确认就发生在这一刻，后端也会校验，缺了它直接拒绝）；没勾就点「保存规则」或「试跑」时，这一行会抖动一下并保持红色描边高亮，给出「还没有确认风险」的红字提示，输入焦点自动落到确认项上，勾上或把复制方式换回不删源的档位后告警立刻复位；② 页面上点「立即运行」时会再弹一次确认框，写明会删除哪个目录里的文件，取消即不执行；③ 正式运行前如果发现同时插着多块打标卷**直接拒绝运行**并说明原因（试跑照常放行，不删任何东西）。规则列表上这类规则会标出「移动模式：会删除 NAS 上的源文件」。

**安全限制**：同步模式禁止以整块打标卷的根目录为目标（等于清空整块盘）；NAS 侧目标要求目录已存在，防止手滑写错路径时在 NAS 上静默建目录。打标接口为 `GET /api/backup/auto`（设备列表 + 打标文件位置 + 状态）、`POST /api/backup/auto/marker`（`mark` / `sub_add` / `sub_remove` / `unmark` / `offline_unmark` / `offline_keep` / `rename`，兼容只有 `marked` 字段的旧前端）、`POST /api/backup/auto/run`（试跑同步返回、正式运行转后台）。打标记录保存在 `GPIO.AutoVolumes`，保存「按键控制」时会显式保留，点一次保存不会把离线列表清空。

## Debug 调试报告

调试页通过只读 `/api/debug/report` 生成白名单诊断报告，覆盖 CPU/coretemp、RAPL、IT87 风扇、SATA/NVMe 槽位、SMART/温度、GPIO 及各项获取失败原因。报告默认只使用后台缓存，不主动执行 SMART 检查或唤醒休眠硬盘，也不会应用、恢复或修改任何硬件配置。

报告不包含硬盘序列号、GPIO 自定义脚本及其名称、凭据或完整配置，可复制或下载后由用户自行提交到 GitHub Issue。插件只打开 Issue 编辑页面，不会自动联网提交报告；报告过长时会要求先复制内容，再打开空白 Issue 页面手动粘贴。

## 安全行为

- 首次应用限制前，将每个 `package-*` 的原始 PL1/PL2 保存到 fnOS 的持久化应用数据目录。
- 复用或恢复原始功耗、风扇状态前会核对当前 CPU；检测到系统盘迁移到不同 CPU 时拒绝写入旧硬件状态。旧配置暂时无法应用时，服务仍以降级模式开放界面，便于重新确认功耗与风扇配置。
- 写入后立即回读校验；任一 Package 写入失败时尝试回滚本轮修改。
- 每 5–300 秒校验并重应用，处理休眠恢复或系统服务覆盖功耗限制的情况。
- 在应用中心停止或卸载时恢复首次安装前捕获的限制。
- 卸载向导默认保留应用数据目录（`var`，含 30 天历史采样）；用户在向导中选择"彻底删除"时才清空，重装默认可延续历史图表。
- 首次启用风扇曲线前单独保存原始 PWM 与控制模式；停止、卸载或关闭曲线时恢复 BIOS 自动模式。
- 温度读取失败、风扇转速丢失或 PWM 写入异常时，将已捕获的风扇通道切到 100% 作为故障保护。
- 兼容 IT87 驱动在 100% PWM 时自动切换到模式 0 的行为；温度回落后会先降低 PWM，再恢复手动曲线模式。
- 不修改 BIOS、GRUB、飞牛系统服务或飞牛温度告警配置。可选地经 DKMS 安装/加载内置 IT87 内核模块（见上）；停止/卸载不卸载该模块。
- Web 后端只监听 `root:www-data`、权限 `0660` 的 Unix Socket；修改接口还要求 fnOS 网关注入管理员身份。
- GPIO 输入端口、按键位和 LED 输出位写死为已核对的硬件映射，用户只能选择动作，不能把界面改成任意 I/O 读写器。
- GPIO 自定义脚本限制为 32 个、名称 64 个字符、正文 64 KiB；脚本通过固定 Bash 入口执行并限制为 30 秒，但仍拥有 root 权限。
- 仓位刷新在独立缓存中执行，不会让状态接口等待 `smartctl`；探测失败时显示“未知”，不会把读取错误伪装成空仓位。

## 内置 IT87 驱动（手工验收）

真机（fnOS + TAD6S4N10G）建议按下列五项验收：

1. **新装无独立 it87 FPK**：卸载独立驱动后安装本插件，确认 `lsmod | grep it87`、风扇页有转速；`/etc/tad-module-it87-managed` 存在。
2. **已装独立 it87-kmod**：先装对方 FPK（存在 `/etc/it87-kmod-kver`），再装/启本插件，确认不会重复 `dkms add` 本插件自己的树（日志含“跳过自建 DKMS”）。
3. **内核升级自愈**：改写或删除 `/etc/tad-module-it87-kver` 后执行模块 start/upgrade，应触发 `dkms install --force` 并写回当前 `uname -r`。
4. **停止/卸载不 rmmod**：停止或卸载本插件后 `lsmod` 仍可见 it87；卸载时可清理本插件写入的 DKMS 注册与 `tad-module-it87` conf，但不得卸载正在使用的模块。
5. **许可**：仓库含 `third_party/it87/COPYING`（GPL-2.0 全文）与 `NOTICE`；根目录 MIT `LICENSE` 不变。

CI 环境通常无目标内核头，无法真编 DKMS；以语法检查、Go/UI 测试与 FPK 内含 `app/it87-src` 为准。

生命周期脚本可使用 `bash -n cmd/* scripts/build.sh` 做语法检查。实际 RAPL/PWM 写入必须在 N100/N150/N305 fnOS 主机上由 root 应用生命周期执行；开发机测试不会写主机功耗或风扇配置。

## 重要限制

降低 PL1/PL2 会牺牲部分峰值性能。不同主板 BIOS 可能锁定 RAPL 或 IT87 PWM，若写入被拒绝或回读值不一致，插件会报告错误而不会伪装成功。N100/N150/N305 之外的处理器必须经过单独验证后才能加入支持范围；多风扇控制仍取决于 IT87 驱动是否暴露完整的 RPM/PWM 通道。硬盘仓位与 GPIO 映射针对 TAD6S4N10G 固定硬件设计；后续若支持其他机型，需要单独提供并验证映射表。
